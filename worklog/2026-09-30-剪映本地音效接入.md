# 把剪映接到聊天里，先把音效这一步走通

## 做了什么

今天从一个空项目开始，做了一套 Windows 剪映的本地 CLI 和 MCP 接入。可以列出草稿、读取轨道和字幕时间点，把音效计划写到工程副本里，再校验和登记到剪映首页。每个音效独立一条轨道，后面仍然可以在剪映里拖动、裁剪、调音量。

依赖已经安装，Codex 配置里也加上了 jianying-local。MCP 使用绝对路径启动，换一个工作目录也能正常握手；重启 Codex 后即可加载，当前聊天已经可以通过 CLI 使用。

拿本机一个口播演示工程做了真实草稿测试。它有 845 秒，原来 2 条轨道、337 个片段、679 项素材都保留，新增了一个测试音效轨道。加密内容和元信息都能读取、重新编码并再次读取，数据一致；源工程核心文件的哈希没有变化。31 项自动测试也通过了。

这次测试副本只留在项目 work 目录，没有登记到剪映首页，更没有给正式工程猜位置加音效。目标工程、音效文件和位置还需要用户明确；原生打开、播放、保存、重开验收也还没做，之后不要把结构校验误当成最终播放验收。

## 为什么做

用户的视频已经在剪映里剪得差不多了，剩下的是音效。他希望直接用聊天安排编辑，又不想为鼠标操作和反复截图付出太多 token，还要保留工程里的轨道方便手动二次调整。所以这次重点放在“读现有工程、往副本追加音效”，而不是重新生成一个扁平视频。

## 值得记住的决策和坑

最开始推荐的 yichen-jianying-edit 和 Jianying Headless，其实是 Skill 和核心引擎的关系。公开版本只适用于很窄的 Apple Silicon Mac 环境，不能直接搬来这台 Windows。最后用了 aoguai 的 pyJianYingDraft fork，把 Git 提交和整套依赖锁住；这个 fork 有可逆 codec，可以在隔离进程里调用本机剪映 DLL。没有打包 DLL，也没有调用鼠标键盘控制。

这台剪映是 11.5.0.14471，高于上游声明的一部分验证范围。好在本机的真实加密草稿往返检查通过了，但这个结论只能代表本机安装和测试过的工程，不能泛化成所有新版剪映都没问题。

保存复杂草稿时，库的完整模板序列化会整理画布、轨道顺序、render_index 和字幕内容。对已有工程来说，这些变化没有必要。我们只让库生成新音频数据，然后追加进原始 JSON 的副本，保留未知字段；逐项比较原轨道和素材，避免“能打开但原剪辑悄悄变了”。

11.5 还有 Timelines/project.json 和主时间线目录。根草稿、主时间线及对应备份必须同步，不然改了根文件却可能看不到新音效。主时间线以外的时间线也跟着完整保留。

重复加音效时，不能继续使用固定的 001_click.wav 路径，否则新副本可能覆盖上一轮已经用上的音效。现在每次构建都有独立的素材目录，这个场景也加了测试。

准备好的计划绑定源草稿和音效哈希，源文件变了就重新准备。新增音效复制到副本内部，本地音视频缺失则停止交付。登记首页前要让用户保存并正常退出剪映，程序检测运行状态，备份索引后只追加一条记录，不碰原工程。

还有个安装小坑：全局 uv 缓存出现“临时文件太多”，直接改用项目自己的 .cache/uv 就恢复了，没有去删用户的全局缓存。

## 一句话亮点

让 AI 直接给剪映工程加音效，每个声音都保留成一条可调的轨道，原剪辑也还在。
